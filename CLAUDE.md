# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See `README.md` for setup, running and general test invocations. Prefer the Hatch scripts defined in `pyproject.toml` for the standard tasks:

```sh
hatch run test [args]    # tests
hatch run lint           # ruff check + ruff format --check + pyright
hatch run fmt            # ruff check --fix + ruff format
hatch run start [path]   # launch the app
```

`hatch run test` accepts unittest args, so a single module or test runs as:

```sh
hatch run test tests.test_app
hatch run test tests.test_app.TestGitNightCommanderApp.test_quit_binding_uses_f10
```

Hatch builds its own virtualenv with the `dev` extra on first use, separate from `.venv` — the lint hook (below) still reads `.venv`, so keep that one set up too (per `README.md`).

## Test stubs

`tests/test_app.py` installs stub `textual` / `rich` modules in `sys.modules` when those packages aren't installed, so the app tests can import `gitnc.app` without the real Textual dependency. If you add new symbols imported from `textual.*` at module load time in `gitnc/app.py`, also stub them in `_install_textual_stubs()`.

## Architecture

Three modules under `gitnc/`:

- **`git.py`** — pure data layer. `GIT` shells out to `git` via `Popen(["git", "-C", path, ...])` + `communicate()`, tracking the live processes so `shutdown()` can end them (see *Quitting during a read*). Tests patch that seam with `tests/gitprocess.fake_git_processes()`. `GitStatus` enumerates porcelain status letters; `GitCode` is a dynamically-built enum of every two-character `staged+unstaged` combination, with `.staged` / `.unstaged` / `.contains()` helpers. `Commit` and `GitEntry` are the dataclasses returned to the UI.
- **`terminal.py`** — POSIX/Windows TTY plumbing for the `Ctrl+O` "previous screen" feature. Uses `pty.fork()` on POSIX to spawn `$SHELL -i`, proxies stdin/stdout, and watches for `PREVIOUS_SCREEN_TOGGLE_KEY` (`\x0f` = Ctrl+O) to terminate the shell and return to the TUI. Independent of Textual.
- **`app.py`** — the Textual UI. `GitNightCommanderApp` owns `repo_path`, a `GIT` instance, and a `Terminal` instance.

**View switching:** a single `ContentSwitcher` toggles between three views: `status-view` (default — file list + inline diff), `history-view` (commit list + commit detail), and `diff-view` (full-screen file diff used in long-list mode). The View menu actions and `_focus_active_view()` route focus per view.

**File-list modes:** `MODE_SHORT` shows the status list beside an inline `FileDiff`; `MODE_LONG` widens the list to full width and routes selection to the full-screen `diff-view` instead. `_set_file_list_mode()` toggles the `.long-mode` CSS class on `#status-view` and reloads. The two modes are a radio group in the File menu: `_file_menu_items()` builds every label through `_menu_label()`, which prefixes a one-cell marker gutter (`MENU_RADIO_ON` / `MENU_RADIO_OFF` for the modes, `MENU_MARKER_BLANK` for plain entries) so all labels start in the same column and the item widths don't move when the mode changes. The labels depend on `file_list_mode`, so the menu is rebuilt via `_refresh_dropdown()` each time it opens.

The two File menu entries (`action_short_file_list` / `action_long_file_list`) are direct sets and nothing else. F3 goes through `action_toggle_file_list` to a pair of carrying variants — `action_short_file_list_inline_diff` and `action_long_file_list_full_screen_diff` — which call `_move_diff_between_modes()` so an open diff follows the user across the switch instead of being closed. Whether a diff *is* open is decided differently per direction: in long mode the full-screen diff owns the screen, so `_diff_entry_if_full_screen_visible()` just asks the `ContentSwitcher`; in short mode the inline panel stays visible after Enter opened it, so visibility alone can't tell "expand this diff" from "widen the list" — `_focused_inline_diff_entry()` also requires the panel to be the focused widget, and F3 with the file list focused is the plain mode switch it advertises. That focus read has to happen *before* `action_close_menus()`, which hands focus back to the active view.

**Menu system:** `MenuBar` (docked top) is built from the `MENU_BAR` table and holds one `MenuLabel` per menu. Each has a corresponding `DropdownMenu` rendered on the `overlay` layer. `toggle_menu()` / `_show_menu_by_index()` manage exclusivity (only one open at a time) and active-class styling. Left/right arrows cycle between menus while one is open (`on_key`); F9 opens the first menu; Escape closes any open menu and otherwise exits the full-screen diff view. Dropdown labels are rendered through `_menu_option_labels()`, which pads each entry to a common width and appends a right-aligned hint column filled by `_menu_hint()`: the shortcut looked up in `MENU_HINTS_BY_ACTION` (built from `SHORTCUTS`, so a menu table never repeats a key), or `MENU_SUBMENU_MARKER` (`▶`) for an action in `MENU_SUBMENU_ACTIONS`, so an entry that opens a nested menu is told apart from a leaf entry. A menu whose entries are all unbound leaves and no submenus keeps its bare labels. `DropdownMenu.show_at()` sizes itself from those rendered labels.

**Nested menus:** a `Submenu` (`name`, `items`, `parent_id`) in the `SUBMENUS` registry is the whole definition of one — today just Options → Theme. Everything else is derived from it: `compose()` mounts a `DropdownMenu` per entry under `submenu.dropdown_id` (`dropdown_<name>`); `submenu.action` (`open_submenu('<name>')`) is what the parent menu's entry runs and what the generic `action_open_submenu()` resolves back through `SUBMENUS_BY_NAME`; and `MENU_SUBMENU_ACTIONS` — the set `_menu_hint()` checks for the `▶` — is built from those actions. The opener cascades the child off the row that runs it: it re-shows the parent under the `MenuLabel` named by `parent_id` (the `OptionList` handler hid it on the way in), hides every *other* dropdown, and places the child at `parent_x + parent.menu_width`, `parent_y + parent.index_of_action(...)` — the row offset cancels the two menus' top borders, so the child's first entry lands on its parent's row. `DropdownMenu.menu_width` is computed from the items rather than read back from the layout, because both menus are placed in the same tick. Widths and heights are in screen cells, which only works because `DropdownMenu` is `position: absolute` — a relative offset would be measured from the *visible* overlay siblings, so a cascade would start one parent-width too far right. `_cascade_x()` flips the child to the parent's left when the right edge would run off screen. The parent label keeps its `-active` class, so the whole trail — bar label, parent row, child — stays visible. Both ways back out of a nested menu — Escape and left — go through `_close_submenu_to_parent()`, which reopens the parent by index and calls `DropdownMenu.highlight_action()` so the cursor lands on the entry the submenu was opened from; only once the parent is showing does Escape close the menus. `_open_submenu()` decides that by looking for a visible dropdown whose id is in the registry, so a submenu never has to record that it is open. Because a cascade leaves two dropdowns open, anything that closes a menu closes them all (`toggle_menu` included) — otherwise clicking the parent's bar label would orphan the child.

**Mnemonic accelerators:** every menu label declares its accelerator Turbo Vision style, with a `&` in front of one character (`"&File"`, `"&Short file list"`). `_split_mnemonic()` strips the marker — it never reaches the screen — and reports the index of the marked character; `_menu_mnemonic_key()` turns that into the key that selects the entry, and `_mnemonic_markup()` wraps the character in the theme's `menu_mnemonic` style as content markup (the style has to read on both the menu bar's `$menu-bar-background` and the dropdown's `$panel` background, which is why the default carries no color). Because markers are stripped before `_menu_option_labels()` pads, an accelerator can't widen a label or shift the hint column. Theme entries declare no accelerator — there are too many themes to spell one — and unmarked labels render untouched.

`Alt+letter` opens the matching top-level menu from anywhere, including while another menu is open (`_open_menu_for_accelerator()`, reached from `App.on_key` before the left/right cycling). Inside an open menu, the bare letter runs the entry (`DropdownMenu.on_key`); every other bare character is swallowed so the app's single-letter bindings (`s` / `u` / `c`) can't fire behind the menu. Only keys whose name equals their character are claimed, which leaves `space` / `enter` to the `OptionList` and lets `alt+letter` — which Textual reports with `character="f"` — bubble up to the menu bar.

Menu chrome is composed once and stays mounted, so `action_set_theme` / `_load_saved_theme` call `_restyle_menu_mnemonics()` to re-render the labels; otherwise they would keep the accelerator style of the theme that was active at compose time.

**Chrome colors:** the menu bar and the footer are painted from four `UITheme` fields — `menu_bar_background` / `menu_bar_foreground` / `footer_background` / `footer_foreground` — which `css_variables()` emits as `$menu-bar-background`, `$menu-bar-foreground`, `$footer-background` and `$footer-foreground` (the last two are Textual's own Footer variables, so the app carries no `Footer` CSS at all). The defaults are `$panel` / `$foreground`, i.e. Textual's Header/Footer palette, so a theme that says nothing about the chrome gets the bars every other Textual app has; `midnight-commander.yaml` overrides all four to `$warning` / `$background` for the MC look. Don't tie the bars to a palette role in CSS (they used to read `background: $warning`): "warning" means cyan in one theme and yellow in the next, so the bar changed color for reasons that had nothing to do with chrome. `MenuLabel`'s hover and `-active` states derive from those two variables — a 15% tint of the bar's own text color, and a full reverse — so they stay legible on any palette.

**Committing:** `action_commit_files()` asks twice, and the two questions are different. The first — only when a target still has unstaged changes — is `Stage N file(s) for commit?`, listing the `git add` commands that would run. The second always comes, after the message dialog: `_confirm_commit()` shows `Commit N file(s)?` over the commands from `GIT.commit_with_selection_commands()`, which is the last point at which the files going into the commit are visible before `commit_with_selection` walks the submodules and commits. The command list comes from that method rather than being rebuilt in `app.py` so the popup and the executor can't drift apart, and the message inside it is cut to `_commit_message_subject()` — its first line, marked with `TRUNCATION_MARKER` when there is more — because the popup renders one command per row and a multi-line `-m` argument would break that. N on it doesn't cancel: `_show_confirm()`'s `on_cancel` reopens the message editor — `CommitDialog`, or the external editor the settings name — on the message just written, so backing out of the confirmation costs nothing. That is the only reason `on_cancel` exists; every other caller wants the default, which hands focus back to the active view.

Cancelling the message dialog rolls the index back to where the flow found it. Both halves of the mutation are undone: `_restore_externals()` re-stages the files it unstaged, and `_unstage_pending()` unstages what the stage confirmation added, from the `_pending_commit_staged` list `_begin_commit_message()` was handed. Without the second half the files stayed staged, so a second `C` on the same selection found nothing left to stage and skipped straight past `Stage N file(s) for commit?` — the question never came back. Only entries that had *nothing* staged before go on that list (`not code.has_staged_changes`): an entry that was already partly staged had its index state built by the user, and `git restore --staged` would throw that away instead of putting it back. `_commit_submit()` clears the list without running it — the files it staged are the files it just committed.

**Writing the message in an external editor:** the Options → Settings section *Commit message editor* is a three-row radio group — `SETTINGS_EDITOR_ROWS` maps each row to `COMMIT_EDITOR_BUILTIN` / `_ENVIRONMENT` / `_COMMAND`, Space picks one, and typing into the `Command:` row under it selects the command option — stored as `commit_editor` plus `commit_editor_command`. Every place the flow used to push `CommitDialog` for a message — `_begin_commit_message()` and the `on_cancel` of `_confirm_commit()` — now goes through `_edit_commit_message()`. That asks `_commit_editor_argv()` for a command line (`$EDITOR`, or the setting, split with `shlex`; `None` means the built-in dialog) and runs it with `_commit_in_external_editor()`: suspended on the previous screen like the drafting tool, with `run_commit_editor()` writing `commit_editor_template()` to a temporary `COMMIT_EDITMSG` (git's name, which is what puts editors in git-commit mode), running `<argv> <path>` and reading the file back through `strip_commit_editor_text()`. The help text and file list sit under git's scissors line (`COMMIT_EDITOR_SCISSORS`) rather than on `#` lines, so a message line starting with `#` survives. The result feeds `_commit_result()` exactly as the dialog's would: an empty message, one that is only the `branch:` prefix, or a failing exit status (`EditorResult.message is None`) cancels; anything else goes to the confirmation. Anything that stops the editor from running at all — unset `$EDITOR`, an empty or unparseable command, `EditorResult.started` false, a terminal that won't suspend — notifies and falls back to `CommitDialog`, so a bad setting never costs the user the commit. `KeyboardInterrupt` out of the editor is read as abandoning it, for the same reason as in the drafting tool. The Draft button lives in `CommitDialog`, so drafting isn't reachable with an external editor.

**Drafting commit messages:** the commit dialog's Draft button (F4) runs whatever tool the user named in Options → Settings. The two settings are free text — `commit_draft_command` (a command line, split with `shlex`) and `commit_draft_prompt` (a template) — rather than the fixed tool list this used to offer, so a tool the app has never heard of works without a code change. In `SettingsDialog` they sit with `commit_draft_parse_suggestions` under `_section_header("Experimental")` — three settings whose behavior depends on a tool the app doesn't ship, kept apart from the branch settings that always work. The prompt is the one row drawn by `_field_rows()` rather than `_text_row()`: a framed field with its label above it and a block caret while the row is under the cursor, because a template is a paragraph and a value trailing a label gives no sign of how much of it is on screen. `_wrap_field_text()` wraps it at word boundaries — not `textwrap.wrap()`, which drops the space after a finished word (that space is what pushes the caret along) and returns no lines at all for an empty value (the field still has to draw one); a word too long to break, a URL or a path, is cut where it fills the line. The field is `SETTINGS_FIELD_MIN_LINES` tall and grows with the value to `SETTINGS_FIELD_MAX_LINES`, past which it scrolls far enough to keep the caret's line on screen — the last lines by default, earlier ones once the arrows have gone up there — and the cap is what stops a pasted-in essay from pushing the rows under it off screen.

The caret is a position in the value (`_caret`), not the end of it: `edit_text()` inserts and backspaces there, and `_caret_markup()` draws it *on* a cell — `UITheme.text_caret` is `reverse` because the character under it still has to be readable. `FieldLine.start` is what connects the two, and `_caret_position()` maps an offset to a line and column with it; on a wrap boundary the two lines share the offset and the caret takes the one it is about to type into. Inside a framed field up and down are `move_caret_line()` and never leave it (up on the first line and down on the last go to the two ends of the value) — Tab and Enter are what leave a row, so the arrows are free to be the caret's. On a one-line row up and down stay the row cursor's, since there is nowhere else for them to go; left and right are `move_caret()` on any text row. `move_cursor()` enters a row with its caret at the end, and `_key_hint()` swaps the key line under the dialog, because the same arrows mean two different things depending on the row. `SETTINGS_SECTION_WIDTH` — the frame's indent plus its borders — is what the section rules run to and what `#settings-body`'s `min-width` is sized for, so nothing here wraps. `request_commit_draft()` invokes the command as `<argv> <prompt>`: `commit_draft_prompt()` joins the template and the filenames going into the commit into one final argument, `run_commit_draft()` runs it with stdin on `DEVNULL` (the run is shown on the terminal but nobody is typing into it, so a tool that decides to prompt would just sit there), and the result comes back as a `DraftResult` — `ok` says whether `text` is a commit message or the reason there isn't one. It is `Popen` plus two `_pump_draft_output()` readers rather than `subprocess.run`, because `run` hands its output over only once the process has exited and the point is to show the tool working: every line goes to the `on_output` callback as it is printed. stdout is the message and stderr is the failure detail, so the two are collected apart even though both are reported as progress; stderr gets its own thread, since draining them in sequence deadlocks as soon as one fills its pipe buffer while the other is being read. `subprocess.run(timeout=…)` used to enforce the deadline — with the pumps blocking on the pipes instead, a `threading.Timer` kills the process and the pumps then end at EOF. A `KeyboardInterrupt` out of the stdout pump is the user pressing Ctrl+C on the previous screen (see below): the tool is killed and the run comes back as cancelled, because letting it escape would skip `App.suspend()`'s resume — Textual's suspend has no `finally` — and strand the terminal outside the alternate screen. `_apply_commit_draft()` passes the output through `_with_branch_prefix()`, because the tool knows nothing about the branch-prefix setting: the branch name goes in front unless the message already starts with it. Both the prefill and the drafted message end up in the same `TextArea`, so either is editable before F2 commits it. `CommitDialog.append_output()` renders the lines into `#commit-output`, a pane that stays hidden (`display: none`) until something puts a line in it, holds the last `COMMIT_DRAFT_OUTPUT_LINES` lines pinned to the bottom, and stays on screen after the run that filled it. Only the worker fills it — see below — so on the normal path the dialog is the message box and nothing else.

**Where the drafting tool runs:** on the previous screen — the same terminal `Ctrl+O` puts a shell on. `_draft_on_previous_screen()` enters `App.suspend()` for the length of the run, echoes the command line (`shlex.join`, i.e. as a shell would show it) and then every line the tool prints through `Terminal.write_previous_screen()`, and only then hands the result to `_apply_commit_draft()`. Two things follow from that: the tool's progress is visible at full screen height instead of in a six-row pane, and it is *still* visible afterwards — the output is in the normal buffer's scrollback, so `Ctrl+O` from the main screen scrolls back to the whole run long after the commit. `write_previous_screen()` reads `sys.stdout` per call rather than capturing it, because `App.suspend()` rebinds it to the real stdout for the length of the block; a closed stream is swallowed, since a commit is not worth failing over an echo.

Showing the output does not replace capturing it — the lines are still parsed into the message, or into the reason there isn't one — but the screen is the only place they are *shown*. `#commit-output` stays empty and hidden on this path: the user has just watched the run at full screen height, and repeating it under the message box buries the one thing the dialog is for. The failure text still comes back through `notify()`, and the run itself is a `Ctrl+O` away. This path needs no `call_from_thread` either: it is inline on the UI thread, which is free precisely because there is no UI to keep responsive while the app is suspended.

`_commit_draft_worker()` is now the fallback for a terminal that can't be suspended: the same tool on a thread worker with the TUI still up, its lines arriving through `_post_draft_output()` — `call_from_thread` like every other worker result, from the worker and from the stderr reader both, and a `RuntimeError` there means the app outlived the run and the line has nowhere to go. `_draft_on_previous_screen()` returns whether it ran, and guards *only* entering the suspension (an `ExitStack` rather than a `with` around the whole thing), so a failure inside the run can't be misread as "never suspended" and send the same tool off to a second run. `RuntimeError` is caught alongside `SuspendNotSupported` there because an app with no driver — one that isn't running, which is every unit test — declines by returning from the context manager without yielding.

**Picking between drafted messages:** a tool asked for several candidates answers with a numbered list, so the third drafting setting — `commit_draft_parse_suggestions`, the "Parse suggestions from numbered list" checkbox — reads the output back into separate messages. `parse_numbered_suggestions()` drops everything ahead of the first number; an item then keeps the blank and *indented* lines under it — that is how a suggestion with a body survives — and ends at the first line back in column 0 that isn't another number. Indentation is what decides it because the alternative, running each item to the next number, made the last one collect the tool's closing remarks ("My pick: #2, because…") and drop them into the message the user picked. Only the item ends there, not the parse, so a tool that comments between its suggestions still yields all of them. `_joined_suggestion()` then dedents the body, since the indent was list markup rather than something the message asked for, and runs the item through `_strip_markdown_delimiters()`: a tool writing a list writes Markdown, and a commit message is plain text, so `**` and backticks come off (`MARKDOWN_DELIMITER_PATTERN`) and a fence line goes whole (`CODE_FENCE_PATTERN`) — stripping only its backticks would leave the language tag behind as a line of the message. Markers are removed one at a time rather than in matched pairs, because an item that ends at the first unindented line can be cut off mid-emphasis. `_` is not in the pattern: it belongs to `__init__` and `test_app.py` far more often than it marks emphasis. An item that was nothing but markup joins to the empty string, which the comprehension in `parse_numbered_suggestions()` already drops. What is left over is a body written without indentation, which reads as the end of its item; the pick is editable before F2, which is the remedy for that and for a tool that numbered something else entirely. `_apply_commit_draft()` branches on the count: more than one opens `SuggestionDialog` over the commit dialog, exactly one goes straight into the text area (nothing to choose between, but the number still comes off), and none falls back to the whole output with a notification — a tool that ignored the request still wrote something. The picker's rows are `_commit_message_subject()` of each suggestion, so a message with a body doesn't push the rest of the list off screen, while the dismissed value is the whole thing. Its `on_key` claims only Escape and the digits (1-9 pick that row); arrows and Enter are left to the `OptionList`, which is what moves and selects. `_apply_commit_suggestion()` puts the pick through `_with_branch_prefix()` like any other draft, and does nothing at all when the user backed out — the tool's output is still in the log pane, so cancelling loses nothing.

**Stash and remote commands:** the Repo menu — `Pull`, `Push`, `Stash`, `Stash pop` — and the letter pairs `p`/`P` and `z`/`Z` reach four actions that act on the repository rather than on the file under the cursor, which is why they are their own menu instead of more File entries. All four confirm through `_show_confirm()` for the same reason the file commands do: the popup is the last place the exact command line is visible, and each of them moves work the file list can't show — stash empties the worktree, pop refills it (and can conflict), pull moves HEAD, push leaves the machine. None of them gets a second free-text prompt: a stash message, or a remote to pick, is what the `Ctrl+O` shell is for.

Three refusals come *before* the dialog, because each would otherwise open a popup over a command that could only fail: a stash with a clean file list, a pop with an empty `stash_entries()`, and a pull or push with no remote (or, for pull, no upstream — `--ff-only` needs a ref to fast-forward to, and the fix is the push that sets one). What the question says is built from the same data: `action_stash_pop()` quotes the `git stash list` line it would reapply, cut to `STASH_PROMPT_MAX_WIDTH`, because which entry is on top is exactly what someone who stashed twice can't remember; `action_push()` says "and set it as upstream" whenever `push_command()` takes its `--set-upstream` shape, since that push publishes the branch rather than updating it.

Pull and push add one thing the other two don't: `_submodule_mismatch_notes()` puts a `-- Warning: submodule '…' is on branch '…' but parent is on '…' --` row under the command, one per submodule sitting on a branch of its own. Both commands move the parent's history past a gitlink pointing into a submodule nobody is on the branch of, so what arrives from the remote — or what the remote is told the submodule should be at — is a commit the checked-out submodule branch may not contain. The status view already carries the same sentence in its warning label, but the confirmation is the last thing between the keypress and the network. Both texts come from `_submodule_mismatch_text()` so they can't drift, and both read the `_submodule_mismatches` cache the status worker fills rather than re-running a `git rev-parse` per submodule on the UI thread. The warning does not refuse: a submodule on its own branch is a normal way to work, and the question is a question.

`GIT.stash_command()` passes `--include-untracked` — the file list shows untracked files, so a stash that left them behind would put away only part of what the user is looking at — and takes a pathspec when files are selected. Submodule entries drop out of a path-limited stash (the pathspec would name a path in another repo) and the dialog says how many were left behind. `GIT.pull_command()` is `--ff-only`: a pull that has to merge leaves the repo in a state this app can neither show nor finish, and refusing is recoverable in the shell one keystroke away.

Pull and push are the two writes that don't run inline. `git add` returns in milliseconds; a network command sits there, and inline it would freeze every key in the TUI, so `_start_remote_command()` hands it to `_remote_worker` (`@work(thread=True, group="git-remote")`) and `_apply_remote_result()` renders through `call_from_thread` like every other worker. It is guarded by the `_remote_running` flag rather than `exclusive=True`, which cancels a superseded worker's asyncio task but not its thread — a second `P` would reach the wire. `_remote_result_summary()` picks the line to notify from which end of the output holds it: the first stderr line when the command failed (git leads with the reason and follows with hints), the last line of either stream when it succeeded ("Already up to date.", the ref update).

**Confirm dialog sizing:** `ConfirmDialog` sizes its own box instead of leaving it on `width: auto`, so the popup matches the file list it is confirming. `text_width()` takes the widest of the prompt, the rendered command lines and the hint, floors it at `CONFIRM_DIALOG_MIN_TEXT_WIDTH` and caps it at the screen (`CONFIRM_DIALOG_CHROME_WIDTH` = the border + padding the box spends, plus `scrollbar_width()` when there are more commands than `CONFIRM_DIALOG_VISIBLE_COMMAND_ROWS` — without that reservation the scrollbar lands past the border and is clipped, hiding the only sign that the list continues). `compose()` sets `body.styles.width` from that number and renders the commands through `command_lines(text_width)`, which cuts anything longer with `TRUNCATION_MARKER` (`…`) in place of the tail, so a truncated filename reads as truncated rather than as a shorter name. Because Textual's box-sizing is `border-box`, the number set on `styles.width` is the outer width and `Widget.size` reports the inner one. With no screen to measure (unmounted, or the stubs in tests) `text_width()` returns 0 and both the explicit width and the truncation are skipped — the CSS `width: auto` sizes the box as before.

**Dialogs:** `ConfirmDialog`, `HelpDialog`, `SettingsDialog`, `CommitDialog` and `SuggestionDialog` are `ModalScreen` subclasses, opened with `push_screen(Dialog(...), callback=...)` and closed by the dialog calling `dismiss(result)`. Each takes its content through `__init__` and renders it in `compose()` — there is no `show()` / `hide()`, and they are not composed into the app's own tree.

Modality is structural: Textual truncates the binding chain at the first modal node (`Screen._modal_binding_chain`), so while a dialog is open the app's `s` / `u` / `c` / Escape bindings cannot fire and the `StatusList` is out of the focus chain. That is why the actions carry no re-entrancy guards and `App.on_key` / `action_escape` say nothing about dialogs. Each dialog handles its own keys in `on_key` and stops every event; don't mix `BINDINGS` into that, because a screen's own bindings are only consulted once the key bubbles to `App._on_key`, which a stopped event never reaches. `CommitDialog` is the exception in both halves: it has no `on_key` — the `TextArea` has to own typing — so its `BINDINGS` are reached normally, which is what makes F2/F4/Esc work while its Draft button rather than the text area holds focus. Priority bindings (F10 quit) are checked before forwarding and still work from inside a dialog.

In tests, the seam is `app.push_screen`: `_mock_app()` replaces it with a `MagicMock`, and `_DialogProbe` reads back the pushed screens and invokes the registered callback (`confirm()` / `cancel()`).

**Git reads run on thread workers:** every git call whose cost grows with the repo — `git status` + the per-submodule branch checks, `git log`, `git show`, and the per-file diff/content reads — runs on a `@work(thread=True, exclusive=True)` worker. Running one inline blocks Textual's event loop and freezes all input until the subprocess returns. Each read is a trio:

- a launcher on the UI thread (`_load_status`, `_load_commits`, `_load_commit_detail`, `_render_entry_into`) that captures any UI state it needs and calls `_new_request(group)`,
- a `_*_worker` that only fetches — it must not touch widgets or read app state,
- an `_apply_*` reached via `call_from_thread` that only renders.

`exclusive=True` cancels a superseded worker's asyncio task, but a *thread* worker keeps running to completion, so two results for one group can arrive in either order. Every `_apply_*` therefore drops results whose serial fails `_is_current_request()`. Because the reload is asynchronous, anything that has to happen *after* it must be passed into the launcher (`_load_status(restore=..., refocus=..., clear_diff=...)`) rather than sequenced at the call site.

Submodule branch mismatches are cached in `_submodule_mismatches` by the status worker; `_update_submodule_warnings()` renders from that cache so resize-driven re-renders never shell out.

Write operations (`stage_entry`, `restore_file`, `delete_file`, `commit_with_selection`, …) still run inline on the UI thread.

**Quitting during a read:** F10 goes through `action_quit`, which calls `GIT.shutdown()` before `exit()`. A thread worker can only be waited for — Textual joins its worker threads during shutdown — so a quit pressed while the startup `git status` / `git log` are still running registered fine and then changed nothing until git returned, which on a large repo is seconds of an app that looks like it ignored the key (and then exits on what feels like the fifth press). `shutdown()` terminates the git processes in flight and makes every later call return the failure shape without spawning one; refusing the next call is the half that matters, because a read is several git commands in a row (`load_status` walks the submodules) and killing only the running one hands the worker straight on to the next. It is what `_run_in()` uses `Popen` + `communicate()` for instead of `subprocess.run()`, and the spawn happens under the same lock the shutdown takes, so a process can't be born into the gap between the flag going up and the set being read. A pull or push in flight is the exception: `action_quit` leaves it alone and waits, because it is a write with half of itself on the wire and the user asked to close the app rather than to cancel the command.

In tests, the seam for the reads is `run_worker` / `call_from_thread`: `_mock_app()` collapses both to a direct call so the worker body and its UI callback run inline, keeping the synchronous call/assert shape. `_install_textual_stubs()` stubs `textual.work` with the same `self.run_worker(partial(...), **kwargs)` shape so both paths behave alike.

**Diff rendering:** `FileDiff.show()` parses unified-diff hunk headers (`@@ -a,b +c,d @@`) to track old/new line numbers and renders each line with a left-side line-number gutter, coloring `+`/`-` lines green/red and stripping the `diff`/`index`/`---`/`+++` headers. `render_commit_detail()` does the same for `git show` output in `CommitDetail` — commit header block and per-file headers bold, hunk markers colored, diffstat graph and patch body colored `+`/`-`, no gutter (the text spans several files). Both take their colors from `_diff_line_styles()` so the two views can't drift apart.

Colors come from the theme, never from git: `GIT._run_in()` invokes `git -c color.ui=false` and strips any SGR escapes that a per-command `color.diff = always` still forces through, because the widgets render git's stdout literally.

## Linting & type-checking

After editing any `.py` file, run both tools on the changed file(s) and fix anything they report before considering the task done:

```sh
hatch run ruff check <file>          # lint
hatch run ruff format <file>         # format in place (no --check)
hatch run pyright <file>             # type-check
```

A `PostToolUse` hook (`.claude/hooks/lint-python.sh`, wired in `.claude/settings.json`) runs these automatically on every `Write`/`Edit` of a `.py` file and blocks the turn with the diagnostics if anything fails. The hook shells the tools out of `.venv/bin/` directly rather than through Hatch, so `.venv` must exist with the `dev` extra installed. When the block fires, fix the reported issues and re-edit — don't just retry the same edit. Use `hatch run ruff check --fix` and `hatch run ruff format` (without `--check`) to apply automatic fixes; address pyright errors manually.

## Conventions

- All git access goes through `GIT` in `gitnc/git.py`. Don't shell out to `git` from `app.py` or `terminal.py` — extend `GIT` instead. `run_commit_draft()` and `run_commit_editor()` are the only subprocesses `app.py` runs itself, and they deliberately aren't git: the drafting tool and the editor are whatever the user named.
- Styling lives inline as `DEFAULT_CSS` on each widget class plus the app-level `CSS` on `GitNightCommanderApp`. There is no external `.tcss` file.
- The `F5` key and the File→Refresh menu entry both map to `action_refresh`, which reloads whichever view is currently active.
- `SHORTCUTS` holds one primary key per action — the one the footer, the menu hint column and the README advertise. A second key for an action goes in `SHORTCUT_ALIASES` (`(key, action)`), which appends a `show=False` binding: the footer keys off the binding rather than the action, so a shown alias would print its action's description twice. Aliases stay out of `MENU_HINTS_BY_ACTION` (one key fits the column) and are folded into the key column of `HELP_SHORTCUTS`, which is what the Help→Keys dialog lists. Three actions carry both today: delete, `F8` because that is where every TUI file manager has put it and `Del` because desktop keyboards have that key; commit, `c` plus `F2`, the key that submits the message from inside `CommitDialog`, so one key opens the flow and closes it; and quit, `F10` plus `q`. The last is there because F10 is not the app's to rely on — a terminal emulator can keep it (VS Code's integrated terminal gives it to the debugger's Step Over and never forwards it), and a key the app never receives is indistinguishable from an app ignoring it. The alias is deliberately not priority, unlike the `F10` binding: priority bindings are checked before the key reaches a modal, so a priority `q` would quit the app out from under someone typing a commit message.
- The key a new action gets follows what the action is about. Function keys are the file-manager verbs this lineage has always put on that row — `F3` view, `F5` refresh, `F7`/`F8` restore and delete — plus the chrome (`F1` help, `F9` menu, `F10` quit). Bare letters are the git verbs: `s`/`u` stage and unstage, `c` commit, `p`/`P` pull and push, `z`/`Z` stash and pop. Within a letter pair shift is the counterpart, so a pair costs one letter rather than two. New keys default to `show=False`: the footer already runs past 80 columns with the eleven it shows, and the menus plus Help→Keys are where the rest are advertised.
- Function keys read `F8`, never `f8`, and shift+letter reads `Shift+P`, never `P` — Textual names the first in lower case and the second as the bare uppercase letter, one cell from its lowercase partner. `_shortcut_key_display()` fixes both for the two places that would otherwise show the raw name: the footer, via each binding's `key_display`, and the key column of `HELP_SHORTCUTS`. It returns `None` for everything else, which leaves Textual's own display alone — `^o` for `ctrl+o` reads better than a spelled-out modifier. The menu hint column doesn't go through it but through `_format_shortcut_key()`, which upper-cases every key it renders and spells shifted letters out the same way (`_is_shifted_letter()` is what both consult).
- To add a nested menu, append a `Submenu(...)` to `SUBMENUS` in `app.py` and point the parent menu's entry at `SUBMENUS_BY_NAME["<name>"].action`. That is all of it — the dropdown widget, the opener action, and the `▶` marker all follow from the registry entry. Don't hand-write a `dropdown_*` widget, a per-submenu `action_open_*_menu`, or an arrow inside a label: labels are padded before the hint column is appended, so a typed-in arrow would widen the entry and push the column out of line.
